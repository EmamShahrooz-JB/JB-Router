توکنی که در پیام گذاشتید (ghp_O7Le...tk0B) معتبر است و دسترسی کامل به حساب شما دارد (همه ریپوهای خصوصی، از جمله jb-mail, JB-VPN-Mother, Shahrooz-Market).

۱. خلاصه اجرایی

JB-Router یک گیت‌وی مسیریابی هوش مصنوعی (AI Gateway) است: یک endpoint سازگار با OpenAI (/v1/*) که درخواست را می‌گیرد، فرمت را ترجمه می‌کند و به ۴۰+ ارائه‌دهندهٔ بالادست (Anthropic, Gemini, OpenAI-compatible, Copilot, Cursor, Kiro, Codex, …) می‌فرستد؛ به‌همراه مدیریت OAuth/API-Key چند‌حسابی، fallback، شمارش مصرف، و یک داشبورد Next.js.

جمع‌بندی من: این پروژه از نظر «مهندسی مسیر درخواست» واقعاً قوی و بالغ است — چند جا کدهایی دیدم (مثل ssrfGuard.js یا custom-server.js) که سطح آن از اکثر پروژه‌های مشابه بالاتر است. اما سه ضعف سیستماتیک دارد:

  1. کاهش کیفیت در لایهٔ «پیرامونی»: ۹۱ خطای react-hooks/set-state-in-effect، ۶۷۵ console.log، ۱۵۸ catch {} خالی، ۸۴ .catch(() => {}) — یعنی خطاها به‌صورت خاموش بلعیده می‌شوند.
  2. تکرار شدید کد (۲۶ کارت CLI تقریباً یکسان، منطق combo دوبار در chat.js) که باعث واگرایی تدریجی و باگ‌های «فقط یکی از دو نسخه اصلاح شد» می‌شود.
  3. شکاف در چارچوب امنیتی/کیفی: هیچ rate-limit روی /v1، هیچ CI‌ای که lint/test را اجرا کند، و ۱۱ آسیب‌پذیری وابستگی (شامل ۱ critical در next و high در undici که موتور اصلی fetch شماست).

SEC-01 · کوکی mimo-login امضا نشده است → Open Proxy / SSRF

شدت: بالا (به‌شرط requireLogin=false) · بردار: شبکه

src/proxy.js قبل از هر چیز بررسی می‌کند آیا کوکی jb_router_mimo_login وجود دارد؛ اگر بله، sessionFromRequest() آن را دیکد می‌کند و مقادیر از payload خود مرورگر (upstreamBase, jar) در ساخت URL بالادست استفاده می‌شوند:

  return attachSessionCookie(await runTakeover(sess, upstreamUrl, origin), sess);

  if (isAccountProxyPath(pathname)) return attachSessionCookie(await proxyAccountRequest(sess, request, origin), sess);

و decodeSessionCookie (mimoLoginSession.js:123) فقط base64url + JSON.parse است — هیچ امضا/HMAC ندارد (فقط TTL چک می‌شود). isAccountProxyPath هم عمداً «همه‌چیز جز مسیرهای خود اپ» را پروکسی می‌کند (mimoLoginSession.js:419-423).

گیت این مسیر، isAuthenticated(request) است که در dashboardGuard.js:182-187 وقتی settings.requireLogin === false همیشه true است. requireLogin=false یک تنظیم رسمی و پرکاربرد است (داشبورد دکمه‌اش را دارد، و برای استفادهٔ LAN/local رایج است). در آن حالت:

# هیچ کوکی/توکن معتبری لازم نیست؛ فقط یک کوکی جعلی base64:
curl 'http://host:20128/anything' \
  -H 'Cookie: jb_router_mimo_login=v2.eyJ0IjoxNzAwMDAwMDAwMDAsInVwZHN0cmVhbUJhc2UiOiJodHRwOi8vMTY5LjI1NC4xNjkuMjU0IiwiaiI6W119'
# ⇒ سرور درخواست را به http://169.254.169.254/... می‌فرستد و پاسخ را برمی‌گرداند

تأثیر: SSRF کامل (شامل cloud metadata روی 169.254.169.254)، open proxy (جعل IP/لاگ، استفاده از سرور شما به‌عنوان relay)، و خواندن پاسخ سرویس‌های داخلی. حتی با requireLogin=true هم هر کاربر داشبورد می‌تواند همین کار را بکند (شدت متوسط).

اصلاح:

  1. کوکی session را امضا کنید: HMAC-SHA256(JWT_SECRET, payload) و در دیکد verify کنید (مثل dashboardSession.js).
  2. upstreamBase را هرگز از کلاینت نگیرید؛ آن را در حالت سرور (map با کلید state) نگه دارید، یا حداقل با allowlist دامنه‌های *.xiaomi* مقایسه کنید.
  3. این branch را به isAuthenticated(request) === true و requireLogin !== false مشروط کنید.
